# Database Design

## Overview

Steam Backlog Manager uses PostgreSQL for persistent storage.

For Version 1, the application stores imported Steam games in a single `games` table. Each row represents one game in the local library.

The backend uses Spring Data JPA and Hibernate to map the Java `Game` entity to the PostgreSQL table.

## Games Table

| Column        | Type    | Description                                |
| ------------- | ------- |--------------------------------------------|
| `id`          | Long    | Primary key generated by the database      |
| `title`       | String  | Name of the game                           |
| `rating`      | Integer | User rating for the game                   |
| `hoursPlayed` | Integer | Number of hours played, converted from Steam's playtime value in minutes.                   |
| `status`      | String  | Current library status                     |
| `notes`       | String  | Personal notes about the game              |
| `steamAppId`  | Long    | Steam application ID                       |
| `imageUrl`    | String  | URL used to display the game's cover image |

## Game Status Values

Games can currently use the following status values:

* Backlog
* Playing
* Completed
* Dropped
* Live Service

## Entity Mapping

The `Game` entity is mapped to PostgreSQL using JPA annotations.

The repository layer uses Spring Data JPA to perform database operations such as:

* Retrieving games
* Saving imported games
* Updating ratings, statuses, and notes
* Deleting games

## Current Relationship Model

Version 1 is a single-user application, so games are not currently associated with individual user accounts.

The current structure is:

```text
games
 ├── id
 ├── title
 ├── rating
 ├── hoursPlayed
 ├── status
 ├── notes
 ├── steamAppId
 └── imageUrl
```

## Version 2 Database Changes

When user authentication is added, the database will introduce a `users` table and associate each game with the user who owns it.

The planned relationship will be:

```text
users
  |
  | 1
  |
  | many
games
```

Each game will contain a user relationship so that different users can maintain separate Steam libraries.

Possible `users` fields may include:

* `id`
* `email` or `username`
* `passwordHash`
* `steamId`

The exact Version 2 schema will be designed when authentication is implemented.
